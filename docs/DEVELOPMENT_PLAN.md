## 1. 제품 목표와 이번 완료 범위

교사가 시험 전에는 예상정답률과 추정분할점수를 설계하고, 시험 후에는 NEIS 자료로 성취평가 결과를 분석해 다음 평가를 개선하는 Windows·macOS 데스크톱 앱을 완성한다. 기본 기능은 인터넷·AI 연결 없이 작동한다. 계산과 제안은 교사의 검토를 지원하며 성적이나 분할점수를 자동 확정하지 않는다.

개발 소스는 [GitHub 저장소](https://github.com/piman-code/goedusplit) 하나로 관리한다. Mac과 학교 Windows PC는 각자의 Git 복제본에서 개발하고, 같은 소스 커밋·버전으로 플랫폼별 설치 파일을 만든다.

이번 완료 범위는 다음으로 고정한다.

- NEIS 정오표·문항정보표 및 선택 자료를 불러오는 성취평가 분석.
- 문항별 예상정답률·목표 성취수준 설정, 전체 분할점수 계산, NEIS 입력표 생성.
- 작업 저장·불러오기, CSV·근거 엑셀 내보내기.
- 예측–실측 비교와 다음 시험 기준표 제안.
- 시험지 HWP·HWPX·PDF에서 번호·유형·배점을 로컬로 읽어 문항 초안을 만들고 교사가 확인하는 흐름.
- 가명 내보내기, 실명 포함 시 확인, 포트폴리오 학생 해시 저장.
- 두 운영체제에서 재현 가능한 개발·테스트·빌드·배포와 실제 설치본 검증.

시험지 오류 점검, 외부 AI·Jev 연결, 클라우드 데이터 동기화, 앱 자동 업데이트는 후속 기능이다. 이번 핵심 버전의 완료 조건에 넣지 않는다. 이 범위 구분은 기존 [README](../README.md)의 현재 제품 범위를 따른다.

### 실행할 Goal과 종료 지점

**권장 개발 Goal:** Goedu-Split의 현재 핵심 기능을 보존·보완하고, Mac과 학교 Windows에서 GitHub 소스로 개발을 이어갈 수 있게 하며, 동일한 커밋·버전의 두 운영체제용 앱을 실제 PC에서 검증해 배포 가능한 후보와 최신 안내를 완성한다.

개발 Goal의 완료는 6절의 필수 조건과 합격 기준을 모두 충족한 **배포 준비 완료**다. 공개 Release 게시, 기존 설치 앱 교체, 유료 인증서 도입은 이후 별도 실행이다. 사용자가 Goal에 공개 배포까지 명시적으로 포함하면 해당 범위와 승인을 계약에 반영하고, 게시·다운로드 검증까지 끝나야 그 Goal을 완료한다.

Windows 실기와 교사 확인은 개발 Goal에서도 필수다. Mac에서 만든 자동 검사나 Windows CI 성공으로 대신할 수 없다. 사용자 확인이 남으면 그 항목을 `사용자 확인 대기`로 기록하며 프로젝트 전체를 완료로 표시하지 않는다. GitHub에서 새 복제본 개발과 CI 검증을 해야 하므로 필요한 원격 push·실행 범위를 승인받지 못한 상태에서는 로컬 준비까지의 부분 완료로 보고한다.

React 원본 복구·큰 화면 파일 분할은 핵심 기능 수정이나 재현 가능한 빌드를 방해할 때만 필수로 승격한다. 근거 없이 모든 구조 개선을 끝내려 하거나 후속 AI 기능을 끼워 넣어 목표를 늘리지 않는다.

## 4. GitHub와 두 컴퓨터의 개발 방식

### 기준

- `main`: 검토·테스트가 끝난 기준 소스. 실제 원격 상태를 확인한 후 이 방식으로 운영한다.
- 작업 브랜치: `codex/<작업명>` 등 작업별 이름. Mac·Windows가 동시에 개발하면 서로 다른 브랜치를 쓴다.
- 변경 제출: 작업 브랜치 → PR → 검사·검토 → `main` 병합. 승인되지 않은 push·병합·릴리스를 실행하지 않는다.
- 같은 파일의 겹치는 부분은 한 작업이 맡는다. 충돌 시 상대 변경을 먼저 읽고 합치며 강제 push로 해결하지 않는다.
- Git은 코드와 문서를 공유한다. 분석 자료·앱 설정·포트폴리오가 자동 동기화되는 기능은 없다.

### 작업을 시작하고 넘길 때

1. 이 문서와 최신 인계 기록을 읽고 `git status`, 현재 브랜치·커밋을 확인한다.
2. 원격 조회 권한이 확보된 세션에서 `git fetch origin`으로 변경을 확인한다. 미커밋 변경이 있으면 먼저 보존한다.
3. 해당 작업 브랜치의 최신 상태를 가져오고 변경 범위·담당 파일을 정한다.
4. 구현 → 변경에 맞는 검사 → 결과 기록 → 커밋 순서로 진행한다.
5. push가 승인된 범위에서 올리고, 다른 PC는 올려진 브랜치와 인계 기록을 받아 이어간다.

작업 인계에는 커밋, 변경 파일, 실행한 검사, 미검증, 다음 첫 작업을 남긴다. 동시에 다른 컴퓨터의 로컬 변경을 직접 동기화하거나 공유 드라이브의 한 작업 폴더를 함께 편집하지 않는다.

각 PC는 별도의 `.venv`를 만든다. `.venv`, `build`, `dist`, 캐시, 앱 설정과 실제 학생·시험 자료는 소스 공유 대상에서 제외한다. `.gitignore`만 믿지 않고 전송 직전 추적 파일과 배포 내용을 확인한다. 공용 인계 문서에는 개인 PC의 절대경로·계정·실명 예시를 넣지 않는다.

## 5. 완료를 위한 작업 순서

상태는 `대기 / 진행 / 구현 완료 / 검증 완료 / 사용자 확인 대기 / 보류`로 기록한다. 체크는 해당 작업의 완료 증거가 모두 있을 때만 한다. 아래 항목은 아직 완료 처리하지 않았다.

### 의존 관계와 진행 규칙

P0~P4는 작업 묶음 이름이다. 숫자대로 모두 마쳐야 다음 작업을 시작한다는 뜻은 아니다. P0의 사용자 데이터 격리를 먼저 끝내고, P1의 합성 소스 검증과 P2의 빌드 준비를 진행한다. 두 플랫폼 후보가 만들어진 뒤 P1의 실기 검증과 P3의 후보 검증을 끝낸다. P4 문서는 각 작업과 함께 갱신하고 마지막에 재현 여부를 확인한다.

| 작업 묶음 | 시작에 필요한 것 | 직접 진행할 주체 | 남겨야 할 산출물 |
| --- | --- | --- | --- |
| P0 환경·문서·격리 | 현재 소스와 기존 변경 보존 | 에이전트 | 개발 안내, 격리 실행 경로, 관련 회귀 검사 |
| P1 합성 소스 검증 | 격리 환경과 기대값이 있는 합성 자료 | 에이전트 | 입력 파일·기대값, 핵심 기능 검사 기록 |
| P2 통합 CI·빌드 | P0 기준, 승인된 원격 작업·빌드 환경 | 에이전트 | 두 OS 검사·빌드 설정, 실행 기록·후보 파일 |
| P1/P3 실제 PC 검증 | 동일 커밋의 두 플랫폼 후보 | 에이전트와 Windows PC 사용자 | 형식·계산·JSON 왕복·설치·오프라인 검증 결과 |
| P4 최종 재현·인계 | 필수 검증 완료 | 에이전트와 교사 | 최신 안내, 알려진 제약, 배포 준비 결과표 |
| 공개 배포 | 배포 준비 결과표와 해당 게시 승인 | 승인 범위의 에이전트 | Release URL·필수 파일·다운로드 검증 결과 |

후속 구현이 승인되면 같은 범위의 수정·검사·기록은 매 단계 재승인 없이 이어간다. 실제 Windows PC·승인·환경 때문에 한 항목이 대기해도, 독립적으로 가능한 문서·합성 검사·빌드 준비를 계속한다. 필수 항목을 조용히 보류하거나 첫 단계만 끝내고 전체 완료로 판정하지 않는다.

### P0. 실행 기준과 검증 환경 정리

- [ ] `README`, `SECURITY`, `QUALITY_AUDIT`, `MANUAL_QA_CHECKLIST`, `HANDOFF`의 버전·AI 범위·테스트 기록을 현재 상태와 맞춘다. 과거 결과는 날짜가 있는 이력으로 보존한다.
- [ ] Mac·Windows 개발 환경 안내를 작성한다. Python·Node·실제 설치 라이브러리 버전을 기록하고 재현 가능한 의존성 기준을 정한다. 기존 Mac 가상환경은 교체하지 않는다.
- [ ] 테스트 실행 경로에서 QSettings, 앱 데이터·포트폴리오, WebEngine 프로필·캐시, AI 임시 폴더를 임시 디렉터리로 격리한다.
- [ ] `CODEX_CLI_PATH`가 있어도 가짜 CLI 테스트가 같은 결과를 내도록 회귀 검사를 보강한다. 실제 AI 호출은 하지 않는다.
- [ ] Windows 로컬 빌드가 Git 복제본에서 실행되도록 소스 키트 감사와 저장소 감사를 구분한다. 현재 `build_windows.bat`는 `.git`·`.venv`를 차단하는 키트 감사를 먼저 실행해 개발 복제본에서도 실패할 수 있다.

완료 증거: 기존 환경을 유지한 새 복제본에서 두 플랫폼의 개발 안내를 따라 실행할 수 있고, 격리된 테스트가 사용자 저장 파일을 읽거나 바꾸지 않는다. 문서마다 같은 제품 범위와 버전을 안내한다.

### P1. 핵심 기능의 실제 사용 검증

- [ ] 합성 정오표·문항정보표·수행평가 자료로 모든 핵심 흐름을 두 운영체제에서 확인한다.
- [ ] 계산기 작업 JSON의 Mac → Windows → Mac 저장·불러오기 왕복을 확인한다. 배점·소수 정답률·검토안·목표 수준이 보존되어야 한다.
- [ ] NEIS 입력표·결과 CSV·근거 엑셀·예측–실측 보고서의 파일 생성과 Excel에서의 열기를 확인한다. 기본 가명, 실명 선택·취소, 수식처럼 보이는 문자열 처리를 확인한다.
- [ ] HWPX·텍스트가 있는 PDF의 문항 초안을 원본의 번호·유형·배점과 대조한다. HWP는 kordoc 존재·부재를 각각 확인한다. 읽기 실패·이미지 PDF 등은 빈 결과를 성공으로 표시하지 않는다.
- [ ] 파일 선택·내보내기 취소·잘못된 파일·저장 실패에서 기존 작업이 보존되는지 확인한다.
- [ ] 1280×800·1366×768 등 실제 노트북 화면, 운영체제 배율, 밝은/어두운 화면, 한글 경로·공백 경로, 탭 전환과 WebEngine을 확인한다.
- [ ] 승인된 실제 시험지는 사용자가 우선 확인한다. 에이전트가 필요한 경우 파일·열람·처리 범위를 별도로 승인받고 로컬에서만 비교한다.
- [ ] 예측–실측 상대차·경계 학생 부족 안내·서답형 묶음·기준표 제안을 교사가 읽고 의미를 확인한다. 기본 기준표의 낮은 수준 정답률은 임의 변경하지 않고 근거를 검토한다.

완료 증거: 같은 커밋의 앱으로 두 운영체제에서 각 항목의 성공·실패·취소 결과를 기록하고, 저장 파일과 화면 결과를 대조한다. 자동 테스트 통과로 실제 사용 검증을 대체하지 않는다.

### P2. 두 운영체제의 자동 검사·빌드

- [ ] 기존 Windows Actions를 유지·보완하고 macOS 작업을 추가한다. 둘 다 동일한 커밋을 빌드하도록 묶는다.
- [ ] PR·변경 시 검사와 버전 지정 시 배포 후보 빌드를 구분한다. 앱 내부 버전, 태그, 파일명·설치 프로그램 버전이 같아야 한다.
- [ ] 각 단계의 실패가 다음 단계를 중단하게 한다. 현재 Windows 글꼴·아이콘 준비는 두 명령이 한 `cmd` 단계에 있고, 설치 프로그램 생성은 `continue-on-error`라 설치 파일 없는 성공을 허용한다. 필수 산출물 검사로 보완한다.
- [ ] 빌드마다 Python·의존성·Node·운영체제·아키텍처·커밋을 기록한다. 오래된 산출물은 새 버전의 성공 파일로 재사용하지 않는다.
- [ ] 빌드·DMG 패키징은 새 작업 디렉터리에서 한다. 현재 스크립트의 `dist` 정리·같은 이름 덮어쓰기를 기존 배포 폴더나 설치 앱에 실행하지 않는다.
- [ ] Python·계산기 테스트, 소스 감사, 빌드 후 감사, 필수 파일 확인, 체크섬 생성을 연결한다.
- [ ] 글꼴·아이콘 준비와 HWP 선택 의존성 처리의 성공·부재·오류를 구분한다.

완료 증거: 동일한 소스 커밋의 macOS·Windows 빌드가 각각 성공하고, 어느 필수 단계라도 실패하면 배포 가능한 성공으로 표시되지 않는다. 후보 파일을 내려받아 설치본 검증까지 이어진다.

### P3. 같은 버전의 배포 후보와 사용자 승인

권장 초기 지원 대상은 현재 사용하는 macOS Apple Silicon과 학교 Windows x64이다. 학교 OS·아키텍처는 실제 PC에서 확인한 후 지원표에 확정한다. Intel Mac·Windows ARM 지원은 각각 별도 빌드·실기 증거가 있을 때만 추가한다.

- [ ] `vX.Y.Z` 한 버전 아래 macOS DMG, Windows 설치 EXE·portable ZIP, 사용 안내, 변경 내용, `SHA256SUMS`를 준비한다.
- [ ] 모든 플랫폼 파일이 동일한 소스 커밋에서 만들어졌는지 증명한다. 한쪽 실패 시 다른 쪽 파일만으로 두 플랫폼 배포 완료를 선언하지 않는다.
- [ ] Actions의 임시 artifact와 사용자용 Release를 구분한다. 현재 Windows artifact 보관은 14일이므로 영구 다운로드 안내로 쓰지 않는다.
- [ ] 다운로드한 배포 후보를 각 실제 PC에서 새로 설치·실행하고, 핵심 흐름과 오프라인 동작을 확인한다. Windows portable은 폴더 전체로 검증한다.
- [ ] Mac의 ad-hoc 서명과 Developer ID 서명·공증을 구분하고 Windows 첫 실행·SmartScreen 안내를 확인한다. 유료 계정·인증서 도입 여부는 별도 결정한다.
- [ ] 검증 결과와 남은 제약이 있는 릴리스 노트·게시할 파일 목록을 준비한다. 원격 초안 Release는 생성 권한이 확보된 경우에만 만들고, 개발 Goal은 로컬 게시 준비안으로도 이 항목을 충족할 수 있다. 공개 배포는 해당 시점의 사용자 승인 후 실행한다.
- [ ] 이전 정상 버전, 설치본·작업 파일의 백업, 되돌리는 절차를 보존한다. 자동 업데이트·자동 설치는 추가하지 않는다.

완료 증거: 동일 커밋의 두 플랫폼 후보·체크섬·게시 준비안이 있고, 실제로 후보를 받은 PC에서 설치·사용·백업을 이용한 복귀가 확인된다. 공개 배포까지 포함한 Goal에서는 게시된 Release의 파일·체크섬과 다운로드 후 실행 증거가 추가로 필요하다. 빌드 성공·배포 준비·공개 배포를 별도 상태로 기록한다.

### 필수 합격 기준

아래 T01~T09를 고정한 기준 커밋의 각 지원 플랫폼에서 확인한다. 입력은 합성 자료를 기본으로 하고 생성 방법·기대값을 기록한다. 코드만 읽고 추정한 결과, 필수 검사 건너뜀, 사용자 확인 대기는 합격으로 처리하지 않는다. 기능 수정 후 그 기능의 관련 검사를 다시 실행하며, 실제 배포 후보가 바뀌면 그 후보를 기준으로 실기 결과를 다시 확인한다.

| T01 분석 | 합성 정오표·문항정보표·선택 수행평가 자료를 불러와 분석 | 입력 학생·문항 수, 총점, 수준별 인원·문항 정답률이 별도로 작성한 기대값과 맞음. 잘못된 파일은 오류를 알리고 이전 정상 분석을 보존 |

| T08 화면·교사 확인 | 실제 PC에서 작은 화면·배율·밝기별 조작, 보정 결과 읽기 | 핵심 버튼·입력·결과를 스크롤·접기로 접근 가능하고 잘림이 조작을 막지 않음. 교사가 예상정답률 설계 → 표 저장 → 시험 후 비교를 완료하고 경계 표본 부족·서답형 안내·참고용 제안의 의미를 확인 |
| T09 빌드·후보 | 같은 커밋·버전의 두 OS 빌드와 받은 파일 검사 | 모든 필수 검사·필수 파일 확인 통과. 버전·태그 또는 후보 버전·체크섬 일치. 개인정보 감사와 파일 구성 검사 통과. 실패를 성공으로 표시하지 않으며 이전 버전 복귀 절차 확인 |

T02의 고정 기대값 예: 같은 유형·난이도의 두 문항을 배점 1·3점, A~E 정답률 `(100, 80, 60, 40, 20)`·`(80, 60, 40, 20, 0)`으로 넣으면 B 원점수 2.6점·100점 환산 65%, NEIS C는 45%다. 별도 4점 문항의 정답률 `(100, 82.5, 63.25, 40, 12.5)`는 입력 C 63.25%를 보존하고 NEIS C 65%·E 15%·A 100%를 표시해야 한다. 이는 현재 계산 계약의 예이며 교육 제도를 새로 정하는 규칙이 아니다.

실제 학교 자료는 교사가 우선 로컬에서 확인하고 비식별 문제 설명만 공유할 수 있다. 원자료를 에이전트나 외부 서버에 전달하는 것은 필수 조건이 아니다. 교사 확인 자체가 남아 있으면 T08과 개발 Goal 완료는 대기한다.

### 완료 보고에 필요한 묶음

개발 완료 보고에는 기준 커밋·버전, 지원 OS·아키텍처, 두 플랫폼 개발 안내, 두 플랫폼 후보 파일·SHA256, 해당 커밋의 검사·CI 기록, T01~T09 결과, 교사 확인, 알려진 제약, 복귀 절차, 릴리스 노트·게시 준비안을 함께 연결한다. 하나라도 필수 증거가 없으면 빠진 항목과 담당자를 적어 부분 완료로 보고한다.

## 7. 검사 명령과 결과 기록

다음은 기존 저장소의 명령이다. 모두 저장소 루트에서 실행한다. 실제 사용 전에 P0에서 테스트 저장 위치 격리를 확인한다. 이번 문서 작성에서는 앞서 확보한 테스트 결과를 재사용했으며 앱 빌드·설치·배포를 실행하지 않았다.

macOS:

```bash
QT_QPA_PLATFORM=offscreen .venv/bin/python -m unittest discover -s tests
node --test tests/test_expected_rate_web.cjs
```

Windows PowerShell:

```powershell
$env:QT_QPA_PLATFORM = 'offscreen'
$env:PYTHONIOENCODING = 'utf-8'
.\.venv\Scripts\python.exe -m unittest discover -s tests
node --test tests/test_expected_rate_web.cjs
```

기존의 수동 스크립트는 `tests/manual_calculator_flows.py`, `tests/manual_laptop_ui.py`, `tests/manual_native_window.py`이며 명시적인 `--run`으로 실행한다. native window 검사는 macOS 대상이다. 2026-10-02 P0에서 세 스크립트의 앱 데이터·설정·WebEngine 프로필·네트워크를 격리했다. 실행 결과와 남은 범위는 GOAL_STATUS를 따른다.

검증 기록은 아래 형식으로 남긴다. 테스트 수 자체를 목표로 삼지 않으며 건너뛴 검사와 이유도 기록한다.

## 8. 권한과 작업 보존

이 문서는 개발 계획을 작성해 달라는 요청의 산출물이다. 미래 작업 목록 자체는 구현·외부 전송·push·병합·배포·설치·인증서 사용·실제 학생자료 열람을 승인하는 계약이 아니다. 후속 실행 요청과 현재 유효한 권한을 확인해 필요한 작업을 진행한다.

### 예상되는 사용자 참여

이 표는 이후 Goal 실행에서 필요한 참여의 안내다. 지금 포괄 승인을 요청하는 것이 아니며, 이미 유효한 승인은 재사용한다.

| 언제 | 사용자가 할 일 | 필요한 이유·확인할 결과 | 이후 진행 |
| --- | --- | --- | --- |
| P0 지원 환경 확정 | 학교 Windows의 OS·아키텍처·앱 실행 가능 여부 확인 | 실제 지원표와 개발 안내를 맞추기 위함 | 에이전트가 해당 환경 기준으로 안내·빌드 구성 |
| P2 원격 검증 시, 아직 승인되지 않았다면 | 특정 저장소·작업 브랜치의 push·CI 실행 변경안을 검토 | Windows 원격 빌드에 필요. 검사된 diff·전송 파일·실행 범위를 그때 제시 | 승인 범위에서 push·실행하고 결과 확인 |
| 두 플랫폼 후보 준비 후 | 학교 PC에서 후보 실행·작업 파일 왕복 결과 확인 | Mac에서 Windows 실제 UI·학교 환경을 대신 검증할 수 없음 | 에이전트가 오류 수정·새 후보·관련 재검증 진행 |
| 핵심 사용 검증 | 설계·분석·보정 흐름을 사용하고 의미 확인 | 수치 통과와 교사에게 유용한지는 별도 증거 | 결과 기록 후 완료 판정 |
| 공개 배포 요청 시 | 게시할 버전·파일·릴리스 노트 승인 | 실제 배포 대상·효과·검증·복귀안을 확인 | 승인 후 게시·다운로드 검증 |

로그인·새 개발 도구 설치·인증서가 실제로 필요해질 때만 구체적인 조치를 안내한다. 자동 빌드로 가능한 일은 사용자에게 수동 빌드를 떠넘기지 않는다. 다른 PC의 사용자 확인을 기다리는 동안 Mac에서 가능한 독립 작업을 계속한다.

기존 앱·소스·stash·원자료·저장 작업을 보존한다. 실제 학생자료가 든 것으로 기록된 stash와 확인 대기 폴더는 임의로 열지 않는다. 설정·포트폴리오 해시 키는 PC별 상태이며 단순 Git 이동으로 연결되지 않는다. 다른 PC로 이전하는 기능이 필요하면 보존·연결·보호 방법을 별도 설계한다.

새 화면·외부 디자인 자료를 쓰는 경우 사용자 제공 AGENTS 지침을 따른다. 기존 디자인 시스템을 우선하고 외부 자료의 출처·변경 내용을 먼저 제시한다. 이번 문서 작성은 화면·디자인 변경을 포함하지 않는다.

## 9. 다음 첫 작업

P0의 **문서 최신화와 격리된 테스트 실행 경로 정리**부터 시작한다. 현재 코드·작업 트리·실제 버전을 다시 확인하고, 테스트 환경 의존성 한 건과 사용자 앱 데이터 접근을 먼저 해결한다. 그다음 Windows Git 복제본 빌드 문제와 두 플랫폼 CI를 연결한다. 이번 대화의 167개·43개 통과 결과는 조건이 바뀌지 않았다면 이유 없이 반복하지 않는다.

이 문서를 현재 개발 계획으로 사용하고 [HANDOFF](HANDOFF.md)는 과거 작업 이력·보존 위치의 참고로 함께 읽는다. 기록이 상충하면 최신 사용자 요청과 실제 파일·실행 증거로 판정한다.
